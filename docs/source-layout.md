# Original source-file layout

The retail EXE was linked from one object file per compiland, and the linker
keeps every object's code together, in source order. The retail .text is
therefore a sequence of contiguous blocks, one per original source file (or per
unity file that `#include`s several). This page records which block is which
file, how that was derived, how sure each row is, and how our `src/` should be
moved to that layout. Batches 1 to 3 of the plan below are partly done.

- Table: [`config/layout-target.csv`](../config/layout-target.csv), one row per
  compiland, and one row per included file inside a unity compiland.
- Tool: `tools/layoutscan.py` (stdlib only, test in `tools/test_layoutscan.py`).
- Unit table: [`config/units.csv`](../config/units.csv), one row per compiland,
  derived from this table by `tools/unitmap.py` (see
  [below](#configunitscsv-and-the-tools)).

```sh
python3 tools/layoutscan.py --batman build/reference/batman-mac --write   # regenerate the table
python3 tools/layoutscan.py --batman DIR --show 0x497c10                   # one compiland, function by function
python3 tools/layoutscan.py --batman DIR --plan                            # migration action per current file
```

The Batman map is private and never committed (see below). Without it the
tool still runs, but only reviewed decisions and Android hints name the rows,
so the committed table is regenerated by someone who has the map.

## Table columns

| column | meaning |
|---|---|
| `start`, `end` | retail VA range (end = end of the last mapped function) |
| `compiland` | proposed path under `src/`: area directory, file name, extension from `language`; empty = undetermined |
| `inner_file` | for a unity compiland: the `#include`d file of this block (`?` = undetermined) |
| `language` | `c`/`cpp` = evidence, `c?`/`cpp?` = default without evidence (see below) |
| `evidence` | `file`, `marker`, `batman`, `batman-sol`, `review`, `android`, `section`, `file-conflict` |
| `confidence` | `high`, `medium`, `low`, `none` |
| `android_unit` | the Android-port unit rows the compiland covers (frozen in `config/layout-android-units.csv`; a hint only) |
| `current_source_files` | our files holding its functions today, with bytes |
| `note` | reasons, conflicts, and the language evidence |

## Evidence, strongest first

1. **Retail `__FILE__` strings** (`file`). The EXE holds 41 source paths, all
   in engine code (asserts and allocation tags). The tool finds every code
   reference to them, so a path names the function that uses it. Absolute
   paths (`d:\projects\game_saga\nu2api.saga\nucore\nufile.c`) give the TT tree
   (`nu2api.saga\`, `gameapi.saga\`); relative ones (`.\pcbatman.cpp`,
   `.\pcapi.cpp`, `.\d3dCore.cpp`, `.\pc\nusound.cpp`) are the primary source
   of a compiland, as the compiler spells the command-line file name. The Mac
   1.0 port (49 paths, private notes) confirms `saga/pcbatman.cpp` and
   `nu2api.saga/nuwin32/{pcapi,windows,d3dApiCalls,d3dCalls}.cpp`.
2. **Unit-start markers** (`marker`). VC8 emits the non-inlined copies of a
   unit's header statics (18-byte fabs, NuFdiv, vector set/copy, `ret`) at the
   start of each compiland; `tools/unitmap.py` finds 131 such clusters. A
   marker proves a compiland start; its absence proves nothing (a file that
   uses none of the helpers has none). A unity file has one marker for all its
   included files, so a long marker-free stretch of engine code that Batman
   attributes to many files is a unity build.
3. **Link order** (structural). One compiland is one contiguous range, so a
   file name can own only one range; the same holds for an included file
   inside a unity. Exceptions are code the linker places by section rather
   than by object: the EH handlers and dynamic initializers at the end of .text
   (one `section` row; the `??__E` initializers prove C++ for their owners and
   are a second link-order witness) and COMDAT inline class members, which
   land with the first object that emits them.
4. **LEGO Batman Mac debug map** (`batman`, `batman-sol`). The 2009 Mac build
   of the next game on this engine is unstripped: every function has its source
   and object file; STABS `SOL` entries name the file `#include`d into a unity
   build. Same-named functions vote for a file; a short run of another file
   between two runs of the same file is a function Batman moved later and is
   folded (`smooth()`); a block is split only where two files form clean
   consecutive runs of three or more. Batman renamed some files when it moved
   them from the game into legoapi (`techno` -> `technos`, `ledge` -> `ledges`,
   `zipup`, `tightrope`, `securitydoor`, `suit`, `shard`, `detonator`,
   `hub` -> `hub_batman`); TCS keeps the older name (`RENAMES`). GCC defers
   inline functions, so `SOL`-based inner files are only `low` confidence, and
   an inner file seen in several blocks keeps only its largest one.
5. **Reviewed decisions** (`review`, the `REVIEW` table in the tool, each with
   its reason): TCS-only files without a Batman counterpart (episodes, chris,
   customise, pursuit, speederchase, starwars_gameai, customiser, simpletons,
   guidelines, hatmachine) named from Android where the name fits the
   alphabetical order of the game library; region directories; joins of
   single-function rows.
6. **Android names** (`android`) only as a hint for undetermined rows. They
   come from `config/layout-android-units.csv`, a frozen snapshot of the unit
   table that `tools/unitmap.py` used to derive from the Android port's file
   tree (329 rows: start, end, Android file name, marker). Its starts are also
   candidate cut points for the scan; the Android tree itself is no input.

Batman's file names win over Android's; retail strings win over both.

## Language (C or C++)

Our mangled names are our own choice, not evidence. Evidence used:

- `cpp`: thiscall member functions, constructors, `??_G`/`??_H` helpers or C++
  EH in the block (C cannot produce them), or a retail `.cpp` `__FILE__`.
- `c`: a retail `.c` `__FILE__` naming the primary file (`rtl.c`,
  `listman.c`), or Batman still a `.c` file (`apiobject.c`).
- `c?`: no C++ construct in the block. TT's 2007 game and legoapi code was
  largely C, Batman converted it to `.cpp` a year later, so C is the default,
  but this is not proof. Do not flip an existing `.cpp` to C (or back) only
  because of this column; see the migration plan.
- `cpp?`: unity files, which Batman builds as `.cpp`. TCS includes `.c` files
  in them (`nufile.c`, `nugraph.c`), so a `.c` unity is equally possible.

## Migration plan

Moving functions between compilands changes code generation, so every batch
is its own commit, verified on its own:

- **Inlining**: VC8 without LTCG inlines only within a compiland. A static or
  small function that moves away from its callers stops being inlined (or
  starts being inlined when it joins them).
- **Header-static copies**: each compiland emits its own copies of the header
  helpers it uses (the markers above). Merging two of our files removes one
  copy, splitting adds one; their symbols in `config/symbols.csv` must follow.
- **Data and strings**: statics, string literals and float constants are laid
  out per compiland; moves change `.data`/`.rdata` order and literal pooling.
- **COMDAT placement** of inline members follows the first object that emits
  them.
- **Fragile functions** that shift with unrelated header or unit changes
  (`FRAGILE` in `tools/unitscore.py`: `SubItemMenu`, `InitGameAfterConfig`,
  `BlockadeRunnerDEjectCreaturePc`, `NuRndrParticleGroup`) are expected to
  flicker; compare them separately.
- **Language**: C and C++ produce different symbols and, in places, different
  code. Changing an extension changes every mangled name in
  `config/symbols.csv` for that file.

**Gate for every batch** (one build at a time):

```sh
git stash -- matching.json 2>/dev/null; cp matching.json /tmp/before.json
make -j2 build && python3 tools/check.py --objects && python3 tools/check.py --format \
  && make lint && make check-core && python3 tools/match.py --update
python3 - <<'EOF'
import json
def exact(p): return {f["address"] for f in json.load(open(p))["functions"] if f["exact_match"]}
a, b = exact("/tmp/before.json"), exact("matching.json")
print("lost", sorted(a - b), "gained", sorted(b - a))
EOF
```

The exact set must be identical by address (gains are welcome, losses block
the batch unless they are FRAGILE functions that come back on a rerun). For a
single move, `tools/unitscore.py snapshot/compare` scores just the objects
involved in seconds; `tools/unitize.py plan|apply|fixconfig` performs a move
into a target file in retail order and rewrites `config/*.json` owners.

### `config/units.csv` and the tools

`config/units.csv` is derived from `config/layout-target.csv`: one row per
target compiland (243), in address order, with the columns

| column | meaning |
|---|---|
| `start`, `end` | compiland range; a unity starts at its reviewed start (its marker), before the first included file's row |
| `unit` | target path `src/<compiland>`; undetermined compilands get the placeholder `src/<area>/?0x<start>`, never a real file and never an Android name |
| `inner_files` | unity compilands only: the `inner_file` values of their table rows, in order (`?` = undetermined). Their ranges stay in the layout table, so a unity is one row here, as it is one object |
| `area`, `evidence`, `confidence` | from the layout table; a unity's confidence is that of its reviewed name |
| `marker` | the unit-start helper cluster at the start, recomputed from the retail .text |
| `functions`, `bytes`, `implemented`, `exact_bytes`, `lost`, `foreign`, `our_files` | measured as before against our current sources (config/symbols.csv and matching.json) |

The EH/initializer section row of the layout table is not a compiland and has
no row. Regenerate after the layout table changes and after a batch (once
`python3 tools/match.py --update` has refreshed matching.json):

```sh
python3 tools/unitmap.py                  # rewrite config/units.csv (needs res/orig for the marker column)
python3 tools/unitmap.py --progress       # compilands whose code is in their target file vs split
python3 tools/unitmap.py --progress --verbose   # ... with the compilands of each class
python3 tools/unitmap.py --show 0x497c10  # one compiland, function by function
```

`tools/check.py` fails when the names or boundaries of `config/units.csv`
differ from the layout table (`python3 tools/unitmap.py --check`); the
measured columns are not checked, they change with every build.
`tools/unitize.py plan|apply ADDRESS` and `tools/unitscore.py compare
--range ADDRESS` take range and target from the row that contains ADDRESS.
`tools/refsyms.py --files` prints the layout table's file next to our file.

`--progress` (243 compilands, at the time of the regeneration):

| placement | compilands | functions | bytes |
|---|---:|---:|---:|
| all code in the target file | 34 | 1,439 | 218,518 |
| same path, other extension (`c?` target, our `.cpp`, or the reverse) | 18 | 1,301 | 376,491 |
| all code in one other file (a rename completes it) | 21 | 317 | 108,848 |

5,549 of 11,496 implemented functions (1.23 of 2.77 MB) are in their target

What depends on names:

- `config/units.csv` `unit` names: written by `tools/unitmap.py` from the
  layout table, validated against it by `tools/check.py`, read by
  `tools/unitize.py`/`tools/unitscore.py` for address lookups. A layout
  change is one `layoutscan.py --write` plus one `unitmap.py`; matching.json
  records the file's hash as an input only.
- Source paths (what batches 1-3 change): matching.json `units` (rewritten by
  `match.py --update`); `config/candidate-only.json` (36 paths),
  `config/code-groups.json` (2), `config/data-members.json` (3), all rewritten

  `tools/check.py`, `tools/lib.py` (debug files, `src/data.cpp`,
  `src/externals.c`, `src/gameapi/saveload.cpp`,
  `src/gameapi/shop_persistence.cpp`), `tools/check_compiler_witnesses.py` (6
